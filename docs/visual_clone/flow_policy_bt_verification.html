Policy-BT verification flow

One generation enters the policy-BT verifier as a copy of its workspace, which the verifier re-executes in its own sandbox with its own venv. The verifier then digests the copy, resolves one task config, writes one screened comparison policy, and compares the generation against every predecessor on a fixed rung ladder. The reward is the arrival-moment win-rate and the gradient is the fold of the per-pair feedback.

Every stage line also goes to the JSON-lines sink <workflow_dir>/<uuid>/verifier_policy_bt.log.

The verifier never mutates the workspace it grades: the run happens on a sandbox copy and a size + head-hash manifest is compared before and after (reexec.py::frozen_manifest), so a mismatch is logged and counts as the crash class manifest_mutated.

Predecessors come from the registry in arrival order (TaskRegistry.previous_generations); a predecessor with no stored digest is rebuilt from its /tmp/mimosa_run_*_<uuid> snapshot when one exists, and is otherwise excluded from the comparison and never fabricated (evaluator.py:587-625). A pair verdict that carries an error field is not cached, so a policy that errors once can still decide the same pair later (evaluator.py:1564).

A cache hit still re-runs the smoke on the newest digest shapes, so a policy written for generation 1 that breaks on generation 2's shape is rewritten (evaluator.py:796-837). The visual_key shape is built inline by VisualChannel.one_order (visual.py:200-208) and is the same key the registry helper documents. The visual list is append-only and scanned for a usable entry, because a cached parse failure never satisfies a hit (evaluator.py:1411-1418).

Amber: the registry is keyed by the goal text, not by the campaign, so a second campaign on the same goal compares against the first campaign's generations and logs a cross-session warning (evaluator.py:640-651); cleanup.sh or a fresh temp root avoids it.
