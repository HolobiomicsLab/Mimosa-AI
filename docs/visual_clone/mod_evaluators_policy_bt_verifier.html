policy_bt_verifier — the BT policy verifier (the verifier in use)

Twelve files turn one generation's workspace into a deterministic digest, re-execute it in a verifier-owned sandbox, then compare it head-to-head with every predecessor through an LLM-written policy and return a win-rate reward. This page follows one generation end to end: thirteen diagrams cover the sandbox, the digest schema, the policy build loop, the metric ledger, the registry caches, the reward guards, the gradient fold and the operator log. Longer explanations are collapsed under each diagram, with the code quoted verbatim and cited by file and line.

Diagram 6 — how the comparison policy is built and accepted

Diagram 6 — policy.py::ensure_policy. the build can fail Cache identity is POLICY_SHA + "_" + recon_version[:8] (evaluator.py::PolicyBTVerifierEvaluator._policy_sha), so a changed recon config invalidates the policy and every cached verdict.

the E48 safeguards, quoted from policy.py
Port of the E45 v3 policy writer with ALL E48 fixes baked in: - Token cap + truncation rejection (safeguard 1): policy-writing calls use ``max_tokens`` 9000 with escalation to 12000; a non-dict / truncated JSON response is NEVER used as code - it fails loudly into the repair loop as a screen-failing sentinel (the E48 regression where a truncated raw JSON text became the policy source). - Real repair plumbing (safeguard 2): every retry passes the exact screen/runtime errors in the prompt AND uses a cache-busting agent role (``_fix<n>``) so a cached broken artifact can never be re-served. - Runtime smoke before acceptance (safeguard 3): a policy must correctly compare 2 real digest pairs (both orders, mirrored winners) before it is used. - AST screen (safeguard 4): stdlib import allowlist + banned builtin names; execution happens in a subprocess with a timeout, cwd = temp dir.

Path: sources/evaluators/policy_bt_verifier/policy.py, module docstring (lines 1–22). The token constants in the shipped code are MAX_TOKENS_FIRST = 12000 and MAX_TOKENS_ESCALATED = 32768 (lines 78–79), so the docstring's older 9000/12000 pair no longer matches the code.

The screen itself, quoted from policy.py::static_screen (line 239): the source must define compare(dA, dB); every import root must be in ALLOWED_IMPORTS (json, math, statistics, re, itertools, collections, functools, copy, typing); a loaded name from BANNED_NAMES (open, exec, eval, compile, __import__, input, breakpoint, exit, quit, globals, locals, vars) is a violation; so is any call to getattr, setattr or delattr, and any __dunder__ name or attribute.

Smoke caps, quoted from policy.py lines 81–88: SMOKE_MAX_DIGESTS = 6, SMOKE_TIMEOUT_S = 30, SMOKE_MAX_PAIRS_CACHE_HIT = 3. The smoke stops at the first failure and includes a self-pair that must return tie.

Diagram 8 — how the metric ledger resolves one metric

Diagram 8 — metrics.py::_resolve_one. ambiguous is not a guess The resolution order is: (1) exact alias hits, (1b) LLM text extraction, (2) strict lexical fallback, (3) log context matching — then ambiguous or missing. The statuses are resolved, ambiguous, missing.

the ledger contract, quoted from metrics.py
The ledger replaces three independent metric-comparison implementations that could silently disagree (the LLM policy's free-form key search, the gradient fold's tie regex, and the evaluator's fuzzy lookup - review §2.2): the policy, the fold and any exploration logic all read ``digest["primary_values"]``. Resolution order per metric (review §4.1): 1. Exact alias hits (file + key), preferring a file that is ``produced_this_run=True``, then a non-verification file (not ``independent_*``/``verif*``/``check*``), then the alias order. 2. Strict lexical fallback only when no alias hits: EVERY core query token (from the metric id) must be present in the candidate key, verification-echo keys are excluded, and ``log_metrics`` are searched too. 3. Several candidates with different values -> ``ambiguous`` (never guess). 4. Nothing -> ``missing``.

Path: sources/evaluators/policy_bt_verifier/metrics.py, module docstring (lines 1–28). The code adds step 1b (LLM extraction from the raw output text) between 1 and 2, which the docstring's four-step list does not name.

Where it is called: evaluator.py::_resolve_metric_ledger (line 895) resolves the current generation and re-resolves every predecessor whose primary_values_version differs from the current recon version. The METRICS stage line reports resolved=… ambiguous=… missing=… with the resolved values and their sources.

Diagram 10 — from pair outcomes to the reward the engine sees

Diagram 10 — two aggregation modes, one reward. cap on weak evidence The default is the raw win-rate: E19c measured it at 0.742 on the frozen arena against 0.643 for the Bradley-Terry fit, which is why the fit is opt-in (policy_bt_reward = "bradley_terry"). the two reward functions and the cap, quoted
def win_rate_reward(outcomes: list[str]) -> dict[str, Any]:
    """Raw win-rate vs predecessors (ties count half; default mode)."""
    n = len(outcomes)
    if n == 0:
        return {"reward": 0.5, "wins": 0, "losses": 0, "ties": 0, "n_pairs": 0}
    wins = sum(1 for o in outcomes if o == "win")
    losses = sum(1 for o in outcomes if o == "loss")
    ties = sum(1 for o in outcomes if o == "tie")
    reward = (wins + 0.5 * ties) / n
    return {"reward": reward, "wins": wins, "losses": losses,
            "ties": ties, "n_pairs": n}

Diagram 12 — the crash rung decides before any LLM runs

Diagram 12 — verdicts.py::crash_rung. crashes decide first The rung returns None when both sides are clean, which is the signal for the pair ladder in diagram 3 to continue.

the crash-rung rules, quoted from verdicts.py
Rules (plan §4 8 / §4b ladder position): - one side crashed, the other clean -> the clean side wins (decisive); - both crashed with IDENTICAL error signature AND crash class -> tie (rule-correct: an environment regression is not a quality difference - chem clintox lesson); - both crashed with clearly different signatures/classes -> decided by partial evidence (fresh artifact counts); equal evidence -> tie. P2.4: when either ledger is a BOOTSTRAP (digest rebuilt from a snapshot, no fresh execution facts) this rung returns ``None`` - "unknown", not "crashed" - and the comparison channel decides.

Path: sources/evaluators/policy_bt_verifier/verdicts.py::crash_rung, docstring (lines 128–145).

Deciding keys this rung can use: exec.error_signature, the crash class and produced_this_run counts. Its verdicts carry channel: "crash_rung", so the pair table shows which rung decided every pair.

Notes and gotchas

Amber: two code-level mismatches are recorded on this page — __init__.py cites a PLAN.md the package does not ship, and the failure_fingerprint in the scores dict is a constant zero stub, so the engine's failure-novelty layer gets no signal from this channel.

Why it matters: the reward is relative to the predecessors seen so far, so overall_score = 1.0 means "beat everything so far", not "good".

Design rules carried over from the offline harness (E44–E48)
  • Re-execution is a rung, not a judge: the crash rung decides only crashes; a bootstrap ledger (no fresh facts) returns unknown.
  • Both orders, always: a mirrored disagreement becomes a tie with a WARNING instead of a coin flip.
  • The policy is code and must pass an AST screen plus a runtime smoke on real digests before it is used; a cached policy re-smokes when a new digest shape arrives.
  • Weak-evidence guard: when every decisive pair rests on self-reported metrics outside the recon primary metrics, the reward is capped at WEAK_EVIDENCE_REWARD_CAP = 0.75.
  • Gold firewall: digests, recon prompts, policy prompts and verdicts never see gold files, labels or grader code.
  • A predecessor with no registered digest and no /tmp snapshot is excluded from the pairs and logged; it is never fabricated.
