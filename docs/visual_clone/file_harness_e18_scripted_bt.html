e18_scripted_bt.py

This file is the E18 producer: for each of the 667 frozen pair plan comparisons it asks the model to pick two comparable files and to write one deterministic Python script, runs that script in a clean subprocess, and records the verdict the script printed. It has five subcommands — status, pilot, run, swap, det — and writes the per-pair ledger results/E18_bt_judgments_2026-09-23.jsonl (L925) plus a cost ledger (L330). The written ledger is what e18_bt_eval.py later fits Bradley-Terry strengths from.

Diagram 1 — 11 boxes. Steps 1 and 2 are merged into one call (protocol key steps_merged L716, SPEC_TEMPLATE L364). Step 3 writes the script (CODE_TEMPLATE L414), step 4 runs it (execute_script L596) and step 4bis repairs it, at most MAX_CODE_ATTEMPTS = 3 times (L78). The vision fallback is reserved for image-primary pairs (L777–L816).

Diagram 3 — 11 boxes. The pilot gate is the third rule: code success at least 0.80 (L1060), JSON parse at least 0.95 (L1061), no snapshot mutation (L1062) and spend at most 1.5 dollars (L1063); all_pass is their conjunction (L1064), and cmd_pilot prints PASS or FAIL from it (L1094–L1095).

Why it matters: the winner comes from the executed script's own JSON line, not from a model opinion, and every prompt carries only the goal, the inventories and the previews (protocol key gold_hygiene in e18_bt_eval.py L432).

Amber: the generated script runs with a stripped environment and a 60 s timeout (L607, L80), but there is no OS-level network sandbox; the file states that limitation itself in the written report of e18_bt_eval.py (L616–L618).

Red: the code prompt demands exactly one JSON line (CODE_TEMPLATE L414, contract line L434 in e18_scripted_bt.py), but parse_script_output tries the last non-empty line and then the whole output joined (L566–L568) and accepts either. A script that also prints its metrics to stdout is still accepted, so the "exactly one line" rule is checked loosely.
