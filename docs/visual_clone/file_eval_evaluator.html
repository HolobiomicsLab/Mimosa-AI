evaluator.py

WorkflowEvaluator is the facade the evolution engine builds once per campaign: it constructs the generic, scenario and verifier evaluators, then routes every evaluate() call by evaluator_type. The verifier channel defaults to HybridVerifierEvaluator; config.verifier_kind = "legacy" swaps in the deprecated VerifierEvaluator and "gold" the oracle GoldFeedbackEvaluator, both through lazy imports. The module also re-exports the public evaluator names for downstream importers.

Main diagram - build three evaluators, route by type

Diagram 1 - the facade has two jobs: build the evaluator set in __init__ (sources/evaluators/evaluator.py:53-121) and dispatch one call in evaluate() (:123-184). The ORACLE branch reads the benchmark gold oracle - leaks gold. Solid arrows are calls, dashed arrows are stored-instance reads; every box also names its real line numbers.

The default run path is the verifier route: the evolution engine always passes evaluator_type="verifier" (sources/core/evolution_engine.py:921-937), and runs the call in asyncio.to_thread only when judge.verifier_kind == "gold"; the generic and scenario routes exist for other callers.

Data flow - what goes in, what comes out

Diagram 2 - inputs, outputs and the files the children write. evaluate() returns a small routing dict; the scores themselves land in the run folder through the child evaluators.

Control logic - the type dispatch and the scenario fallback

Diagram 3 - the dispatch tree of evaluate(): type check (sources/evaluators/evaluator.py:150-155), scenario gate and fallback (:158-171), verifier route (:173-175), generic default (:177-179).

Amber: the fallback at lines 170-171 and the generic default at line 178 discard their child's return value. GenericEvaluator.evaluate() returns None and writes the scores to state_result.json, so the dict this facade returns for those two routes carries evaluation_type and uuid only, with no score inside.
