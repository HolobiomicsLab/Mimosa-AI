claims.py

This file writes the two claim prompts, screens the judge's replies and validates the ladder claims. It runs inside ClaimsEvidenceLayer._extract and ClaimsEvidenceLayer.revise (layers.py), once per task plus once per refinement round. The package view is on mod_evaluators_hybrid_verifier.html.

Diagram 1 — the batched-screen reply path: first balanced block, then a verdict list

Diagram 1 — 7 boxes. Both new helpers are private: _first_json_block keeps a top-level verdict array that the object-first base.extract_json_payload collapsed into a nested object. No test calls the two helpers directly; test_validate_claims_drops_generic_claims and test_is_generic_claim_batch_llm_screen drive them through _screen_call with array-shaped stub replies (tests/hybrid_verifier_test.py:325, 360).

Diagram 2 — data flow: what comes in, what goes out

Diagram 2 — 6 boxes. The registry JSON path is built in registry.py (task_key = sha256(goal + version)[:16]); this file only sees the rows the caller loaded. The two judge screens do issue their own calls through the injected llm_text.

Diagram 3 — control logic: the shape loop, the screens and the count contract

Diagram 3 — 12 boxes. The composition mandate is checked only when the caller asks for it, and an unmet mandate returns the ordered claims with the error, so layers.py:269 keeps the best effort after its retry budget. Test test_validate_claims_drops_generic_claims covers the drop and the floor (tests/hybrid_verifier_test.py:325).
