harness/__init__.py — the empty package marker

The file is empty: zero bytes, zero lines, no docstring and no re-exports. The question this experiment answered is what such a file actually buys the harness. Answer: it turns harness/ into a regular package so that two scripts can write from harness import metrics, while the other 40 harness scripts skip the package and insert the directory on sys.path themselves.

Design — hypothesis, inputs, stages, artifacts

Diagram 1 — 7 boxes. Violet = hypothesis, steel = file, mint = the call form the package enables, amber = what the package does not provide, dashed = expected behaviour. The only code path is the import itself: with experiments_verifiers on sys.path (run_e1.py L29) or both paths inserted (run_e2.py L26–27), Python executes the empty __init__.py and then metrics.py. Related pages: exp_harness_import.html, exp_metrics.html, exp_run_e1.html, exp_run_e2.html.

Why it matters: the empty marker plus the two explicit sys.path.insert lines are the whole import contract of this harness. There is no central place to add a cross-module dependency, which is also why the shim in exp_harness_import.html has no callers.
