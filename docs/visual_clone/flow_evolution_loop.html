Evolution loop

One round of EvolutionEngine.evolve_generation turns generation N into generation N+1. The verifier scores the workspace, writes a textual gradient, the archive accepts or rejects the offspring, and VariationEngine builds the prompt for the next genotype. This page follows that cycle and the QD filter that decides which genotypes stay.

The loop: generation N becomes N+1

Diagram 1 - the closed loop. The dashed grey gradient text path is the only feedback the mutator receives: it reads WorkflowInfo.abstracted_textual_gradient and never touches the verifier's score vectors.

The reward travelling from the verifier to the archive is a scalar; the per-claim scores behind it stay in the verifier, and the mutation prompt sees the gradient text only, cut to 2 048 characters.

Archive and QD selection filter

Diagram 2 - the QD filter inside SelectionPressure.validate_survivor. A rejected offspring returns admit_rejected = True and the archive keeps its previous members. novelty_comparison = "previous_n" swaps the archive k-NN peers for the last N genotypes.

is the gradient fed whole or summarized?

Stored whole, fed summarized on the mutation path.

  • The verifier stores the full text under abstracted_textual_gradient in the run's state_result.json (sources/evaluators/hybrid_verifier/evaluator.py:492) and writes it to sources/workflows/<run>/<uuid>/textual_gradient.txt (HybridVerifierEvaluator._write_artifacts).
  • WorkflowInfo.abstracted_textual_gradient (sources/core/workflow_info.py:166) reads the state key first, the sidecar file second.
  • Mutation path: VariationEngine.mutation_prompt cuts the text to 2 048 characters and replaces _ with a space (sources/core/variation_engine.py:402-407). No other summary is computed.
  • Crossover path: each parent's gradient goes in whole, with no character cap; only the fallback (stderr tail) is cut to the last 1 024 characters (sources/core/variation_engine.py:486-489).
  • Measured size: the gradient quoted below is 4 428 characters, so the mutation prompt received roughly the first 46 % of it.

where the raw scores stay inside the verifier
  • Per-claim score vectors live in the per-task registry hybrid_registry_<16-hex>.json (TaskRegistry.load, sources/evaluators/hybrid_verifier/registry.py:74), written by TaskRegistry.record_generation and read back by TaskRegistry.previous_generations on the next round.
  • The LLM-written policy-scorer scripts are stored in that same registry (TaskRegistry.set_scorer, registry.py:207), and the scorer runs as a subprocess with a 60 s timeout (hybrid_verifier_scorer_timeout_s).
  • The engine reads only two values from the verifier: the scalar overall_score (WorkflowInfo.overall_score, workflow_info.py:122) and the gradient text. No module in sources/core/ imports sources/evaluators/hybrid_verifier/; the engine reaches it only through sources/evaluators/evaluator.py::WorkflowEvaluator.evaluate.
  • Inside the verifier, sources/evaluators/hybrid_verifier/aggregation.py::win_rate_reward turns the score vectors into the reward (temporal_winner decides each pair at the earliest differing stage).
  • Leak to state clearly: the gradient text itself does contain claim scores and evidence lines (for example score: 1.000). The mutator sees those numbers inside the gradient, but never the scorer code or the score vectors.
