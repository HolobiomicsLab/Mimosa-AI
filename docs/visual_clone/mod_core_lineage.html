Lineage and identity

Every evolved workflow is a folder named by a UUID, and two sidecar schemes give it a past and a score. sources/core/lineage.py writes lineage_<uuid>.json with kind and parents; sources/core/workflow_info.py reads the folder lazily and returns the reward; sources/core/schema.py holds the dataclasses that carry uuid, cost and lineage into the evolution loop.

How a failed generation enters the lineage

When the factory raises an error without an encoded UUID, WorkflowOrchestrator._parse_generation_error returns the literal uuid generation_failed (orchestrator.py line 222). The engine still calls record_lineage with that uuid, the run's parents, its evolution_kind and its iteration (evolution_engine.py lines 612-619). record_lineage writes only when the folder <workflow_dir>/generation_failed/ already exists, and that folder is created later in the same iteration by write_run_metrics, which runs folder.mkdir(parents=True, exist_ok=True) (evolution_engine.py lines 708, 1201; run_metrics.py line 29). So the first failure of a run folder leaves no record, and every later failure overwrites lineage_generation_failed.json. Every failed slot reuses one uuid string, so a run folder keeps one such node, carrying the last failure's parents.
