lineage.py

Writes and reads the small lineage_<uuid>.json sidecar that records which parent(s) produced a workflow and by which variation operator. The evolution engine calls record_lineage right after a workflow gets its uuid, so even a run that later fails keeps its place in the tree. The lineage module page and evolution-loop flow place this file in the wider loop.

Diagram 1 — 8 boxes. scan_all calls load_lineage once per folder (line 156) and _read_workflow_goal once per folder when a goal filter is set (line 154). Both read helpers return None instead of raising.

Diagram 2 — 6 boxes. Config fields read: none — callers pass workflow_dir in (sources/core/evolution_engine.py:506, sources/utils/evolution_tree.py:150). Files written: exactly one, lineage_<uuid>.json. The module creates no directory: it returns None when <workflow_dir>/<uuid>/ does not exist (lines 62-65).

Diagram 3 — control logic: write guards and scan filters

Diagram 3 — 10 boxes. The write path fails soft on every guard: a missing uuid, a missing folder or an OSError all return None (lines 57, 65, 84), and only an unknown evolution_kind is repaired rather than rejected (lines 58-60). The scan returns {} when workflow_dir does not exist (line 146).
