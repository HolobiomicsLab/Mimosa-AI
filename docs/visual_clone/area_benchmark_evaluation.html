Batch running and grading

This page maps the batch running and grading area: the CSV-driven task loop, the execution sandbox, and the ScienceAgentBench graders. One helper, grade_directory, grades a folder for two callers: the per-generation ablations and the gold-feedback oracle verifier. Read it before touching csv_mode.py, snapshot_grading.py or the graders.

Diagram 1 - batch pipeline

Diagram 1 - 11 boxes. Step symbols: CsvEvaluationMode._generate_task_science_agent_bench builds the prompt, ExecutionSandbox.run_generated_code and ExecutionSandbox.run_eval_script run the two subprocesses; sources/benchmark_evaluation/csv_mode.py::CsvEvaluationMode._process_single_task_once holds this order. Concurrent mode (run_concurrent_eval_loop) runs the same steps under an asyncio.Semaphore. The capsule is graded by a direct CapsuleEvaluator call in _evaluate_with_science_agent_bench; each non-best snapshot goes through grade_directory (Diagram 3).

Diagram 2 - sandbox vs host boundary

Diagram 2 - the dashed line is a process boundary, not a security boundary. sources/benchmark_evaluation/execution_sandbox.py::ExecutionSandbox._subprocess_env copies the host environment for the child.

Diagram 3 - one grader, two callers

Diagram 3 - 8 boxes. sources/benchmark_evaluation/snapshot_grading.py::grade_directory is imported by csv_mode.py and by sources/evaluators/gold_feedback/grader.py (default grade_fn of grade_private_copy). It does not call save_results(), but ExecutionSandbox.run_generated_code still replaces pred_results/ in the graded folder, so the gold path grades a private copy from make_private_copy. oracle - leaks gold the lower path feeds the benchmark verdict back into evolution; see mod_evaluators_gold_feedback.html.

Provisioning changes committed in 4020790: pins deepchem<=2.7.1, torchdata<0.10, tensorflow-probability<=0.24.0; IMPORT_NAME_REMAP adds skgstat -> scikit-gstat and osgeo -> gdal; EXTRA_DEPS adds deepchem -> pyyaml and phonopy -> seekpath. pipreqs now sees nested worker scripts, an AST scan adds remapped imports that pipreqs dropped, and _subprocess_env sets TF_USE_LEGACY_KERAS=1. What it isolates: the dependency set (own venv), the working directory (capsule copied to /tmp/mimosa_sandbox_*/execution or /eval), the GPU (CUDA_VISIBLE_DEVICES="") and the process group (SIGKILL on timeout). Caller timeouts: CapsuleEvaluator passes 900 s for VER and 300 s for the grader. Tests: tests/test_sandbox_provisioning_pins.py (20 tests), tests/test_sandbox_source_build_constraints.py.

sources/benchmark_evaluation/codebert_scorer.py

Scores generated code against the gold code with CodeBERT token embeddings.

167 lines · functions: calculate_codebert_score, preload_codebert_model · model: microsoft/codebert-base

signatures and the scoring rule
calculate_codebert_score(generated_code_path, gold_code_path) -> float
preload_codebert_model() -> tuple | None

Rule: tokenize both files to max_length = 512, drop padding with the attention mask, L2-normalize, take the best cosine match per token in both directions, then report the F1 of precision and recall. The tokenizer and model load once per process behind a lock.

It raises on failure; CapsuleEvaluator.calculate_codebert_score owns the 0.0 fallback and records the reason in CBS_error.

Precedence rules for reading a graded run

Quoted from AGENTS.md, section "Auditing finished runs", evidence map:

`ablations` outranks the verifier reward — it is what the benchmark actually graded. `source` is `snapshot` (genotype re-graded) or `capsule` (final submission). `ver_success` / `sr_success` / `total_eval` semantics are undocumented: quote them, don't interpret them.
The capsule defines the task result, not the last generation folder. Read the prediction artifacts' headers/first rows; they ground every claim about what was delivered.
Artifact presence ≠ run success: errored rounds (`on_error: true`) can still leave complete outputs.
A round with `on_error: true` has no `evaluation.txt` and no gradient — the run-time error cause is not recorded anywhere; say so instead of guessing.

Order matters: read ablations[] first, then the capsule evaluation_results.json, then the per-round folders.
