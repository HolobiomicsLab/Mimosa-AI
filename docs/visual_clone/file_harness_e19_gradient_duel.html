e19_gradient_duel.py

Runs the four-way gradient duel: the same E16 v2 judge prompt is fed four gradient texts (E19 hybrid, E18 scripted, E15 preference, verifier rubric) and only the gradient text varies. It is the only E19 script whose E19 side makes new LLM calls; the other three sides should be cache hits. Run with uv run python experiments_verifiers/harness/e19_gradient_duel.py.

Diagram 1 — what the file does

Diagram 1 — 8 boxes. main L85 drives the flow in this order: build_quads (L37), the per-quad worker one (L89–99), 4 judge results per quad, then the paired statistics (L119–150), the verdict (L185–201) and the two writers. The E16 cache ledger is shared, so unchanged prompt/input pairs cost nothing.

Diagram 2 — 8 boxes. The judge call and its cache row belong to e16_gradient_audit.py; this file only counts the new calls and their reported cost (L155–161). CAP_USD = 3.0 (L32) is flagged against the new-call cost at L179, not enforced during the run.

Why it matters: the duel holds the judge prompt and inputs fixed and varies only the gradient text, so a relevance delta is attributable to the gradient, not to the instrument.

Amber: the three non-E19 sides are expected cache hits; if the E16 cache is missing, this script silently pays for them and the new-call counts grow. The script reports the counts but does not stop on a cache miss.

Red mismatch: CAP_USD = 3.0 (L32) is only written into the output as a flag (within_cap, L179); this file never raises or aborts when the cap is passed.
