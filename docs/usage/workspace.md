# Workspace & audit trail

Every Mimosa run produces a complete audit trail: what was planned, what
was generated, what executed, what was scored, and what the final state
looked like. This page maps out where each artefact lives.

## The three storage locations

```
sources/workflows/<uuid>/    # per-generation: genotype + state + lineage + memory
runs_capsule/<capsule_name>/ # per-run archive snapshot
sources/memory/              # LLM call cache + task checklists (cross-run)
```

Plus the Toolomics-managed workspace at `Config.workspace_dir` where
generated workflows actually read and write data.

## Toolomics workspace

`Config.workspace_dir` (set per machine, typically pointing inside the
Toolomics install) is the **live working directory** during execution.
Generated workflows write intermediate files, downloads, scripts, and final
outputs here.

When a generation finishes, the engine **snapshots** the workspace into
`sources/workflows/<uuid>/workspace_snapshot/` so the verifier and any
future replay can recompute claims against the exact state.

## `sources/workflows/<uuid>/`

One folder per generation. Contains everything needed to understand that
generation in isolation:

| File / dir | Contents |
| ---------- | -------- |
| `workflow_genotype_<uuid>.py` | The Python source of the workflow that was executed. |
| `state_result.json` | Per-claim scores, agent outputs, status flags. |
| `evolution_prompt_<uuid>.md` | Exact prompt sent to the LLM to produce this workflow. |
| `lineage_<uuid>.json` | Parent UUIDs + operator (`seed`/`mutation`/`crossover`). |
| `memory/` | Per-agent thought + tool-call traces (for `memory_explorer`). |
| `reward_progress.png` | *(only on the best UUID)* score across iterations. |
| `evolution_tree.png` | *(only on the best UUID)* rendered lineage tree. |

A "best UUID" is the one selected at termination — its workspace snapshot
becomes the run's final state and is what gets archived to
`runs_capsule/`.

## `runs_capsule/<capsule_name>/`

When a run finishes, the workspace contents are copied into a timestamped
capsule for long-term storage:

```
runs_capsule/clintox_multitask_20260115_113303/
├── workflow.py
├── results/                # workspace snapshot
├── logs/
└── evaluation_results.json
```

Capsules are intended for:

- Sharing a complete reproduction.
- Comparing two runs of the same task.
- Submitting to a benchmark grader (PaperBench expects this layout).

`<capsule_name>` is generated by the `capsule_namer_model` LLM from the
task description — short, human-readable, and prefixed with timestamp.

## `sources/memory/`

Cross-run state that doesn't belong to a single generation:

- **LLM call cache** — keyed by prompt hash. Prompt-cache-compatible so the
  same prompt at the same provider returns instantly on a second call.
- **Task checklists** — the per-task verifier checklist (`task_hash`),
  built once on first encounter and reused across `--learn` iterations.

## What the verifier consumes

When the verifier scores a generation, it reads:

1. **`state_result.json`** — for the agent's claims.
2. **Workspace snapshot** — for files to verify executable claims against.
3. **Perspicacité** — for literature grounding on soft claims.

It writes back **only** to the evaluation fields in the response — not to
the workspace. The mutator sees the `abstracted_prompt_gradient`, not the
raw verifier output.

## Resetting between benchmarks

For unbiased benchmark evaluation, run

```bash
./cleanup.sh
```

before kickoff. This deletes `sources/workflows/`, the session archive,
the LLM-cache memory, and `runs_capsule/` so cached workflows from
previous runs don't contaminate similarity-based parent selection.

!!! warning "Don't delete by hand"
    `cleanup.sh` knows which directories are runtime state vs. source.
    Wiping `sources/` indiscriminately removes things like
    `sources/prompts/` and `sources/modules/` that you actually need.
